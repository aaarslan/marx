# Building Marx with Wails

This branch targets native Windows x64 using Wails 3.0.0, Go 1.27.3 and Bun 1.4.4. The React interface runs in the installed Microsoft WebView2 runtime. No Electron or Node installation is required by end users.

## Prerequisites

- Windows 11 x64 with WebView2.
- Go 1.27.3 and Bun 1.4.4 on PATH.
- NSIS 3.12 for the installer. Set `NSIS_EXECUTABLE` if makensis is not on PATH.
- The official Checkmarx CLI is a runtime requirement for real scans; Marx never downloads it.

`GO_EXECUTABLE` can select an installed Go toolchain without recording local paths in the repository.

```powershell
bun install --frozen-lockfile
bun run typecheck
bun run test --pool=threads --maxWorkers=2
bun run build
go test ./native ./tools/resources
bun run audit
go install golang.org/x/vuln/cmd/govulncheck@latest
govulncheck ./native ./tools/resources
bun run dist:win
```

The output is `dist/Marx.exe`, `dist/marx-core.exe` and `dist/Marx-0.9.0-win-x64-setup.exe`. Both executables must be distributed together. The NSIS installer includes only those two executables and its uninstaller. It installs per user, offers a destination picker, and retains application data on uninstall. Close Marx before replacing a running build. Installers remain unsigned.

The Wails CLI is not required. Windows resources are generated by the minimal Go tool in `tools/resources`, avoiding the CLI's unrelated template and release-tool dependency graph.

## Architecture

Wails and Go provide the window, native dialogs, clipboard, notifications, browser integration, single-instance handling and Windows DPAPI. The existing TypeScript scan/workbench backend is compiled into `marx-core.exe` with Bun, including SQLite and the report worker. Go communicates with this sidecar over inherited stdin/stdout pipes. There is no application HTTP listener. A Windows job object terminates the sidecar and its child processes when the host exits.

This is a Wails desktop migration with a compiled Bun sidecar, not a full rewrite of the workflow engine in Go. The sidecar still carries a JavaScript runtime. Backend failures are returned to the interface; credentials travel to the DPAPI helper through stdin, never command-line arguments. A new `MarxWails` profile is used; Electron settings and encrypted credentials are not migrated.

## Runtime verification

Use a disposable `MARX_USER_DATA_DIR`; never point verification at real application data. Production builds have no acceptance debugging endpoint. To run the native synthetic acceptance harness, build a separate acceptance executable with `go build -trimpath -buildvcs=false -tags production,acceptance -o <temporary-directory>/Marx-test.exe ./native`, place the compiled `marx-core.exe` beside it, set `MARX_TEST_EXECUTABLE` to that test executable, and run `bun run verify:runtime`. The harness creates synthetic fixtures and enables a local WebView debug port only in the acceptance build.

Test logs, profiles, customer findings, screenshots containing local paths, and machine-specific inventories must remain outside tracked files. Publish portable result summaries only. Earlier Electron validation is historical and does not establish Wails coverage. See [Wails migration validation](wails-migration.md).
